# Substitute School Director Authority

**Status:** accepted
**Date:** 2026-08-15; amended 2026-08-17

Private Business / Product Owner approved a constrained substitute-authority model for School Director-required commands. Each School retains zero or one active School Director. Only an able active Director, otherwise one valid Acting authority, otherwise one valid Temporary authority may be the Effective Director Authority for the exact School, command, and time; all other cases deny. The model is deliberately not a role, membership, generic delegation, emergency override, or additional active Director.

An Acting record identifies the unavailable active Director and a distinct same-School substitute with a fixed reason code and optional expiry. Active Director Availability is separately audited and created atomically by the authorized Director or ESAO Admin action; System Admin cannot change it. Substitute expiry, revocation, or supersession does not restore availability, and only explicit authenticated return/resumption does. A Temporary record identifies an eligible authenticated Finance Officer or School Admin of the same School, a required Active/Acting-unavailability basis, and a mandatory expiry. Subject-eligibility loss permanently invalidates either authority. Replacement and correction are atomic immutable supersessions, as is separate `AUTH-05` conversion; failure leaves the prior authority unchanged.

The stable `AUTH-14` command family has actor-specific variants: an active School Director uses `DIRECTOR` for self-service Acting appointment, ESAO Admin uses `ESAO` to create/manage Acting authority, and ESAO Admin alone uses `TEMP` for Temporary authority. Cross-tier records may coexist only when precedence resolves one effective holder; same-tier duplicates, contradictory state, and multiple effective holders deny. Records use the fixed `SCHEDULED`, `IN_FORCE`, `REVOKED`, `EXPIRED`, `SUPERSEDED`, `INVALIDATED`, `ENDED_ON_RETURN`, and `CONVERTED` lifecycle; failed attempts are audit outcomes. Every lifecycle action requires fresh reauthentication, structured reason, revision update, integrity digest, and immutable audit event. `AUTH-15` remains limited to `AUTH-09`, `AUTH-11`, `AUTH-12`, and `AUTH-18`, with all underlying person-level SoD binding. This ADR authorizes governance reconciliation only, not RBAC, schema, or application implementation.
